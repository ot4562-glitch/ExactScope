# ExactScope model-surface negotiation v0.1

Status: experimental host/build contract. This document does not promote any runtime artifact or target to stable support.

## Purpose

A constrained model should not be handed an ambiguous mix of tool schemas, grammars, prompts, hot-set metadata, and runtime binaries. ExactScope therefore binds the model-visible surface as an explicit host-side contract. The target runtime does not parse this contract and gains no code or resident-memory cost from it.

The v0.1 negotiation rule is deliberately strict:

```text
exact contract id + exact contract version + exact asset digest
```

There is no "close enough" schema compatibility, version range, semantic repair, or fallback to a broader surface.

## Contract file

New capability bundles generated by `tools/compile_capability.py` contain `surface-contract.json` with:

- format `exactscope.model-surface.contract`, version `0.1`;
- negotiation mode `exact-version-and-digest`;
- capability profile id, revision, and domain;
- ExactScope ABI revision;
- hot-set format/version and binding digest;
- one record for every model-facing tool schema, grammar, and prompt fragment present in the bundle;
- an explicit contract id/version and SHA-256 for every listed asset.

The capability profile binds the complete contract through `bindings.surface_contract_sha256`. The capability manifest independently hashes the contract and each payload. A host must reject a mismatch at any layer.

## v0.1 asset contracts

| Asset | Contract id | Version |
| --- | --- | --- |
| `xs-calc.tool.json` | `exactscope.xs-calc.tool` | `0.1` |
| `xs-eval.tool.json` | `exactscope.xs-eval.tool` | `0.1` |
| `xs-calc.gbnf` | `exactscope.xs-calc.gbnf` | `0.1` |
| `xs-eval.gbnf` | `exactscope.xs-eval.gbnf` | `0.1` |
| `prompt-fragment.txt` | `exactscope.prompt-fragment` | `0.1` |

A bundle lists only assets exposed by that selected capability. Missing `xs_find`, an omitted `xs_calc`, or an omitted semantic surface can be intentional specialization and must not be synthesized by the host.

## Host acceptance

A host may declare the exact contract versions it understands with an `exactscope.model-surface.acceptance` v0.1 document. The checked-in example is `spec/examples/model-surface-acceptance-v0.1.json`.

Static compatibility can be checked with:

```text
python3 tools/check_model_surface_compat.py <capability-bundle> --policy <acceptance.json>
```

The checker verifies bundle integrity first, then rejects unsupported ABI revisions, hot-set format versions, or asset contract versions. It never instantiates or executes the runtime.

The JavaScript reference host performs the same surface-contract checks in its file-verification phase, before `WebAssembly.compile`.

## Legacy immutable bundles

Capability revisions created before this contract remain immutable. Their existing manifest and digest verification remains valid, but absence of `surface-contract.json` means they cannot claim explicit v0.1 model-surface negotiation. Do not rewrite a frozen revision to add the file. Generate a new capability revision instead.

## Change rules

A change that alters accepted request shape, grammar language, prompt contract semantics, or interpretation of a model-facing asset requires review of its asset contract version. Byte-only regeneration that preserves the same contract still changes the asset digest and therefore the immutable bundle identity.

ABI, hot-set identity, operation revisions, and kernel IDs remain separate compatibility dimensions. This contract does not authorize renumbering or silent semantic changes.
