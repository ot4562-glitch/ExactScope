# Security policy

ExactScope `v1.0.0-rc.3` qualification is closed and remains prerelease/historical evidence, not a stable supported production runtime. Active rc4 design adds a **grounding trust boundary** in front of the model: private/source scope, provider output, authority/freshness/conflict policy, evidence serialization and prompt-injection handling must be explicit. Evidence is data, never executable instructions. The existing quantitative boundary still requires fail-closed parsing, no semantic repair and no arbitrary code execution. Exact built-artifact, fuzz/sanitizer and representative target evidence still control any Tier 1/Tier 2 or production-security claim.

## Reporting a vulnerability

Use GitHub's private vulnerability-reporting or Security Advisory mechanism for this repository. Do not publish exploitable parser, ABI, memory-safety, or pack-validation details in a public issue before maintainers have had a reasonable opportunity to investigate.

A useful report includes:

- affected commit/version/specification;
- target architecture and toolchain;
- smallest reproducing pack, frame, request, or ABI call;
- observed status, crash, trap, memory behavior, or semantic violation;
- expected fail-closed behavior;
- whether the issue is reproducible in fused, dynamic, native, or Wasm mode.

Do not include API keys, personal data, proprietary model prompts, or unrelated device data.

## Security boundary

ExactScope assumes these inputs may be hostile:

- user questions and optional model-generated retrieval rewrites;
- local/private source content;
- retrieval-provider results, snippets and metadata;
- remote/search/provider responses;
- evidence text containing prompt-injection-like instructions or markup;
- source/revision/freshness metadata;
- dynamic `.xsp` pack bytes;
- Tiny JSON generated by a model;
- TinyWire frames received from another process/device;
- C ABI pointers, lengths, structure sizes, flags, and values;
- caller-provided arenas and scratch buffers;
- aliases and UTF-8 metadata;
- model-selected quantitative operation keys and argument order.

ExactScope does not assume that evidence or a pack is safe merely because it is signed, retrieved from a configured source, or returned by a high-similarity provider. Structural validation, scope policy and evidence-policy checks are always required.

## Required security properties

The implementation and host integration must:

- scope private/user/tenant sources before retrieval and never merge evidence across scopes implicitly;
- never send private query/evidence content to a network provider unless the product policy explicitly authorizes that provider and scope;
- serialize evidence as **untrusted data**, not as model instructions, and keep system/developer Grounding Policy at a higher instruction priority than retrieved text;
- use deterministic escaping/delimiting/model-projection rules, while explicitly treating prompt-injection resistance as an end-to-end property to test rather than claiming delimiters make injection impossible;
- never let evidence text grant tool/network permissions, broaden security scope, or declare its own authority;
- bind requests, provider calls and caches to the effective security scope and reject cross-scope reuse unless the host has an explicit sharing/equivalence policy;
- distinguish authoritative vs supplemental behavior per target/source binding and never silently elevate supplemental evidence to authority;
- distinguish `grounded`, `none`, `ambiguous`, `conflict`, and `unavailable` per target; authoritative `none` requires completed/sufficient required coverage, while timeout/error/denied/budget/incomplete coverage remains `unavailable`;
- apply bounded evidence/candidate/query sizes and reject or type-fail oversized/incomplete provider responses before model-context assembly according to the frozen profile;
- freeze provider/index/preprocessing/ranking identity for qualification and never treat similarity score alone as proof of truth or compare uncalibrated scores across providers;
- never execute native code, Wasm code, scripts, or host expressions from a scope pack or evidence source;
- validate every offset, length, count, index, and multiplication before access/allocation;
- reject malformed UTF-8 and duplicate/overlapping pack sections;
- statically validate VM stack and resource bounds before registration;
- enforce independent runtime instruction/vector/stack limits;
- avoid unbounded recursion, loops, memory growth, or parser nesting;
- return typed errors for malformed input rather than panic/trap;
- prevent Rust unwind or C++ exception propagation across the C ABI; abort-only builds must make malformed input non-panicking and treat any actual panic/abort as a conformance failure;
- avoid reading or writing outside caller-declared buffers;
- avoid retaining request, result, scratch, or temporary pointers after a call;
- zero or fully initialize public result structures on failure;
- perform no network, filesystem, process, clock, environment, telemetry, or random access in the minimum kernel;
- expose no memory addresses or host-sensitive details in wire errors;
- keep adapters from silently repairing/coercing invalid values or source authority;
- fuzz pack loading, grounding-frame parsing/serialization, TinyWire decoding, Tiny JSON parsing, and public ABI boundaries.

## Pack integrity versus authenticity

The `.xsp` CRC detects accidental corruption; it is not a signature. Hosts that install packs from an untrusted distribution channel should verify release SHA-256 values or signatures according to their own update policy before mounting.

The minimum ExactScope core does not require cryptographic signature verification because that would enlarge the most constrained artifacts. Signature verification may be supplied by the host or an optional adapter. Even authenticated packs remain untrusted parser input.

## Denial-of-service controls

Default hard caps are specified for:

- pack size and section counts;
- mounted pack count;
- operations and aliases;
- query/request bytes;
- VM instruction count and stack depth;
- scalar/vector argument counts;
- vector length;
- output/frame size;
- parser nesting.

The host should apply its own request-rate and transport timeouts. ExactScope core is synchronous and does not create threads.

## Deterministic semantic failures

A security issue includes a path where malformed or ambiguous input receives a plausible successful number instead of a typed failure. The project treats silent coercion, method guessing, overflow wraparound, unsupported-unit acceptance, or stale operation identity as correctness and trust-boundary violations.

## Unsafe code

Unsafe Rust is limited to reviewed ABI and memory adapters. Every unsafe block must document:

- pointer provenance and alignment;
- byte length and lifetime;
- non-overlap assumptions;
- mutability/exclusivity;
- how invalid host input is rejected before dereference.

Core numeric, VM, constraint, and pack-semantic modules should forbid unsafe code.

The current source enforces this boundary mechanically: kernel, pack, Tiny JSON, packc, and conformance crates use `#![forbid(unsafe_code)]`; native C ABI and Wasm memory-boundary crates use `#![deny(unsafe_op_in_unsafe_fn)]`. `tools/audit_security_surface.py` additionally checks the public native/Wasm export registry, C header/Rust `no_mangle` parity, and `# Safety` contracts on every public unsafe C entry point. This is a source-boundary audit, not a substitute for sanitizer/fuzz/target testing.

## Release security gates

Before the first stable runtime release:

- parser/ABI fuzz targets exist;
- malformed-input regression corpus passes;
- native sanitizers or equivalent memory tooling run where available;
- Wasm malformed-input tests produce no unexpected traps;
- the **built** native artifact symbol table matches the reviewed export allowlist;
- dependency and license inventory is published;
- release artifacts have checksums;
- dynamic and fused packs produce identical results for any shipped dynamic path;
- support claims match recorded compatibility evidence.

Current code-side groundwork includes strict Tiny JSON/TinyWire/parser regressions, source/header export allowlisting, capability/release archive malformed-file rejection, dependency attribution checks, deterministic checksums, and explicit build-input identity metadata. The full release security review remains open until fuzzing, sanitizer/equivalent memory checks, exact built-artifact symbol inspection, malformed runtime execution, and release-artifact evidence are completed for the artifact being promoted.

## Out of scope

ExactScope does not secure the entire surrounding AI product, model weights, microphone/camera pipeline, operating system, transport encryption, remote provider itself, or final natural-language response. The host remains responsible for authentication/authorization and source access. ExactScope's grounding contract makes scope, authority, evidence identity and failure states explicit; the quantitative subsystem provides deterministic typed results once the host supplies a valid operation and arguments.
